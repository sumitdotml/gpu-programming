The work is not the machinery

Two hierarchies that are easy to blur: the work you launch (grid → blocks → threads) is logical; the hardware that runs it (GPU → GPCs → SMs) is physical. Block scheduling connects them at run time. Barrier synchronization is a different thing: threads of one work group waiting for each other.

    Scheduling ≠ synchronization

    Both involve "when does a thread run", which is why they get mixed up. They answer different questions.

    AspectBlock scheduling · where can this block run?Barrier synchronization · who must I wait for?
    Who does itThe GPU's block-scheduling machinery, at run time. Your code does not call it and cannot pick the SM.Your kernel code, by calling __syncthreads() or, with clusters, cluster.sync().
    UnitA whole block goes to one SM. With clusters, a whole cluster goes to one GPC.The barrier's scope. __syncthreads(): one block. cluster.sync(): every block in one cluster.
    GuaranteesAll of a block's threads are resident on the same SM together, so they can share that block's shared memory and use its barrier.__syncthreads(): no thread of the block passes until every non-exited thread of that block has reached the same call, and memory accesses before it are ordered before those after it among the participating threads (NVIDIA §5.4.4.1). cluster.sync(): all threads of the cluster's blocks have arrived and, per PMPP, their DSMEM operations are complete; NVIDIA adds that all the cluster's blocks have started.
    Does not meanEvery thread runs an instruction at the same instant, each thread gets its own core, blocks on one SM are synchronized, or blocks finish in order.__syncthreads() says nothing about other blocks, even ones on the same SM. cluster.sync() spans blocks, but only those in its own cluster; other clusters are not included. Neither is an "SM barrier" or a "GPC barrier". A grid-wide barrier is a separate Cooperative Groups feature that needs a cooperative launch.

    The work side. matmul() launches gridDim = (2, 2) and blockDim = (3, 3): four blocks of nine threads, 36 threads. Each thread computes row_index from .y and col_index from .x. 20 threads pass row_index < 5 && col_index < 4 and each writes one element of out_d. The other 16 skip the body. Per block: (0,0) 9 in bounds, (1,0) 3, (0,1) 6, (1,1) 2.

    • Rows and columns of out are not hardware positions. The 6×6 picture is your index space. Nothing in the chip is arranged in rows of 3 threads.
    • Placement isn't drawn because your code doesn't decide it. Each of the four blocks goes whole to some SM at run time. Two might share an SM or each get their own, and that can change from run to run. Any placement you see in the map above is illustrative.
    • Your kernel needs no barrier. Each thread reads M_d and N_d from global memory and writes its own out_d element. No thread reads a value another thread wrote, there is no __shared__ array, and there are no clusters. Adding __syncthreads() would not fix or improve anything here.
    • Where your data lives: M_d, N_d and out_d point into global memory (off-chip DRAM). accumulator, row_index, col_index and k are per-thread automatic variables, which PMPP §5.2 says normally live in registers.

    What the picture is careful about

    • Fictional hardware. 2 GPCs × 2 SMs, 2 resident blocks per SM in step 3, and every block placement are made up for teaching. They are not a device spec. Real numbers on this page are labeled with their source: H100 has 132 SMs in 8 GPCs with 128 streaming processors per SM (PMPP p. 68), split into 4 processing blocks of 32 (PMPP p. 76). The warp size is 32.
    • Arrows mean different things. A box inside a box means "part of". A dashed magenta arrow means "assigned to by the scheduler". A solid ochre arrow means "reads or writes". Hatching means "waiting".
    • GPC is not a thread-block cluster. A GPC is a hardware group of SMs. PMPP spells it GPU Processing Cluster and NVIDIA's guide spells it Graphics Processing Cluster. A thread-block cluster is an optional group of blocks in your launch (compute capability 9.0+, starting with Hopper) that the hardware places inside one GPC. GPCs as a hardware grouping are older than that feature. PMPP's wording ("starting with the Hopper architecture, the SMs … are grouped into GPCs") can be read otherwise. I have not checked the GPC history against a primary NVIDIA document.
    • The runtime is software on the host. Your CPU code calls the launch, and the CUDA runtime and driver hand it to the GPU. The CPU does not send threads one at a time. Assigning blocks to SMs happens on the GPU side; NVIDIA's 2009 Fermi whitepaper calls that unit the GigaThread global scheduler. PMPP calls the whole system the "CUDA run-time system".
    • Three different memory scopes. Registers hold one thread's private variables. Shared memory is allocated per block, carved out of the SM's on-chip storage, which also serves as L1 cache. Global memory is off-chip DRAM that every SM can reach. "Local memory" is something else again: private per-thread storage the compiler uses for things like automatic arrays (PMPP §5.2). It is not another name for the SM's L1/shared storage.
